## What you are building

A **relay** is a small server that lets players host a game without opening a port on their home router. The host's game dials OUT to your relay; joiners connect to your relay, which
forwards the bytes to the host. The game's own end-to-end encryption runs through the relay, so you cannot read or change game data, passwords or tokens. Optionally the relay also shows
a list of public games. There is no default relay in the game: nobody uses yours unless a player types its address. Design and threat model: `csharp/migration/design/RELAY.md`;
every option: `csharp/Unciv.Relay/README.md` and `--help`.

You need one Linux server with a public IP address (a small VPS is enough; 1 vCPU and 512 MB RAM handle the default limits) and, for setups A and B, a domain name you control.
Everything below is typed on that server, as a user who may run `sudo`, unless a line says "on your own computer".

## Choose your setup

| | Setup A: behind nginx (recommended) | Setup B: relay alone with a certificate | Setup C: no domain |
|---|---|---|---|
| You need | a domain name; nginx 1.21.4 or newer | a domain name | nothing but the server's IP |
| Who holds the TLS certificate | nginx (Let's Encrypt) | the relay (Let's Encrypt) | the relay (generated by itself) |
| Pick it when | you already run nginx, or want certificate renewal handled in one place | you want the fewest moving parts | you only want to try it, or play with friends |
| What players type | `unciv-relay://relay.example.org:47830` | `unciv-relay://relay.example.org:47830` | `unciv-relay://203.0.113.10:47830?fp=<fingerprint>` |
| Public port | nginx listens on 47830 (or 443, see "Sharing port 443") | the container publishes 47830 | the container publishes 47830 |

If unsure, take **A**. Do not put a Cloudflare-style HTTP proxy (orange cloud) in front: the relay speaks raw TCP, which those do not carry. A DNS-only record is fine.

## Placeholders used in this guide

Replace these everywhere you see them. Nothing in the repository contains anyone's real domain.

| Placeholder | Meaning | Example |
|---|---|---|
| `relay.example.org` | the DNS name of your relay | `relay.mygames.net` |
| `203.0.113.10` | your server's public IPv4 address | the one your hosting provider shows |
| `abuse@relay.example.org` | an address players can write to about abuse | `me@mygames.net` |
| `/opt/unciv` | where you clone the code | any folder you own |

## Step 1: prerequisites

Install git and Docker Engine with the Compose plugin (version 2; the command is `docker compose`, with a space). On Debian or Ubuntu:

```
sudo apt update
sudo apt install -y git curl ca-certificates openssl
curl -fsSL https://get.docker.com | sudo sh
sudo systemctl enable --now docker
docker compose version
```

`docker compose version` must print a version (2.x or newer). For other systems follow https://docs.docker.com/engine/install/. Podman works too (`podman compose`, or the same
commands with `podman`); on a host with SELinux nothing changes because compose.yml already labels the certificate folder.

For **setup A** also install nginx with its stream module, and certbot:

```
sudo apt install -y nginx libnginx-mod-stream certbot
nginx -v
```

`nginx -v` must say 1.21.4 or newer (Ubuntu 22.04 ships 1.18, which is too old: use Ubuntu 24.04, Debian 12 or the packages from https://nginx.org/en/linux_packages.html).
Check the modules: `nginx -V 2>&1 | tr ' ' '\n' | grep stream` must list `--with-stream` (on Debian and Ubuntu the `libnginx-mod-stream` package provides it as a loadable module and
`nginx -T | grep ngx_stream` shows it loaded).

For **setup B** install only certbot: `sudo apt install -y certbot`.

## Step 2: DNS

Skip this step in setup C.

At your DNS provider create an **A** record `relay.example.org` pointing to `203.0.113.10` (and an **AAAA** record for the server's IPv6 address if it has one and your firewall allows it).
Proxying must be OFF (DNS only). Wait until the name resolves, on your own computer:

```
dig +short relay.example.org
```

It must print `203.0.113.10`. (No `dig`? `nslookup relay.example.org` works too.) Certificates cannot be issued before this works.

## Step 3: firewall

Open these ports on the server's firewall **and** in your hosting provider's network settings (many providers have a separate "security group" or "firewall" panel):

| Port | Why | Setups |
|---|---|---|
| 22/tcp | SSH, so you do not lock yourself out | all |
| 80/tcp | Let's Encrypt validates your domain here, and renews | A, B |
| 47830/tcp | the relay tunnel: players connect here (use 443 instead if you follow "Sharing port 443") | all |

Do NOT open 47831 (the read-only HTTP side) or 47832 (the relay behind nginx): they are published on 127.0.0.1 only and stay private. With `ufw`:

```
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 47830/tcp
sudo ufw enable
sudo ufw status
```

Docker writes its own firewall rules for ports it publishes on 0.0.0.0 and these bypass ufw. That is why compose.yml publishes on 127.0.0.1 unless you change it on purpose (setups B and C do).

## Step 4: get the code

```
sudo mkdir -p /opt/unciv && sudo chown "$USER" /opt/unciv
git clone --branch csharp-migration --single-branch --depth 1 https://github.com/Kenmura/UncivSharp.git /opt/unciv
cd /opt/unciv/csharp/Unciv.Relay/deploy
ls
```

`ls` must show `Dockerfile  compose.yml  .env.example  nginx  ...` (use `ls -a` to see `.env.example`). Every command below that mentions `docker compose` is run in this folder,
`/opt/unciv/csharp/Unciv.Relay/deploy`. The image is built from the code you just cloned, in one step, on your server: nothing is downloaded from a registry except the .NET base images from Microsoft.

## Step 5: configure the relay (.env)

All settings live in one file, `.env`, next to compose.yml. It is ignored by git, so `git pull` never overwrites it and your settings never get committed.

```
cp .env.example .env
nano .env
```

Every `UNCIV_RELAY_<NAME>` line is the relay option `--<name>` (upper case, `_` for `-`); an empty value means "the relay's default", and `.env.example` explains each one with its default.
Set at least these, depending on your setup (lines not mentioned stay as they are):

| Variable | Setup A (nginx) | Setup B (certificate) | Setup C (self-signed) |
|---|---|---|---|
| `UNCIV_RELAY_TLS` | `none` | empty (delete `none`) | empty (delete `none`) |
| `UNCIV_RELAY_PUBLIC_NAME` | `relay.example.org` | empty (taken from the certificate) | `203.0.113.10` |
| `UNCIV_RELAY_CONTACT` | `abuse@relay.example.org` | the same, with your address | the same, with your address |
| `UNCIV_RELAY_PROXY_PROTOCOL` | `true` | empty | empty |
| `UNCIV_RELAY_TRUSTED_PROXY` | leave as shipped | empty | empty |
| `UNCIV_RELAY_CERT` | empty | `/certs/fullchain.pem` | empty |
| `UNCIV_RELAY_KEY` | empty | `/certs/privkey.pem` | empty |
| `UNCIV_RELAY_SELF_SIGNED` | empty | empty | `true` |
| `RELAY_TUNNEL_PUBLISH` | `127.0.0.1:47832` | `0.0.0.0:47830` | `0.0.0.0:47830` |
| `RELAY_HTTP_PUBLISH` | `127.0.0.1:47831` | `127.0.0.1:47831` | `127.0.0.1:47831` |

Why these matter:

- `UNCIV_RELAY_PUBLIC_NAME` is the name hosts sign when they log in. It must be the exact name players type in the relay address, or hosts are refused with `bad-signature`
  (see Troubleshooting). Several names are allowed, comma-separated.
- `PROXY_PROTOCOL` and `TRUSTED_PROXY` (setup A): nginx tells the relay each player's real address in a PROXY protocol header, so that limits and bans apply per player and not to nginx.
  The relay accepts that header only from `TRUSTED_PROXY` addresses; the shipped value is the private networks Docker uses for its bridge, which is where nginx's connection appears to come from.
  The shipped value is only safe while `RELAY_TUNNEL_PUBLISH` stays on `127.0.0.1` (setup A): if you publish the tunnel on `0.0.0.0` together with `PROXY_PROTOCOL`, anyone with a private source address could forge a client address. If your logs show every player with the same address `172.x.x.x`, or `proxy` errors, see Troubleshooting.
- `RELAY_TUNNEL_PUBLISH` is `host-address:host-port`; the container always listens on 47830 inside. `[::]:47830` also publishes IPv6.

Optional but useful: `UNCIV_RELAY_NAME`, `UNCIV_RELAY_MOTD`, `UNCIV_RELAY_LISTING` (`open`, `allowlist` or `off`: the public game list), the limits (`UNCIV_RELAY_MAX_ROOMS`, ...), and
`UNCIV_RELAY_MAX_GIB_PER_MONTH` if your server's traffic is metered.

## Step 6: start the relay

```
docker compose up -d --build
```

The first run downloads the base images and compiles the relay: a few minutes. Later runs reuse the cache. Then:

```
docker compose ps
docker compose logs relay
```

`ps` shows the container `Up ... (healthy)` after about 40 seconds (`starting` until then). The log shows `LISTENING tunnel 47830` and `LISTENING http 47831` (and, in setup C, `RELAY-FINGERPRINT ...`). With Podman, `compose ps` shows only `Up`; `podman healthcheck run unciv-relay-relay-1` or `podman inspect` shows the health.
If the container keeps restarting, the log says why in plain words (for example `choose a TLS mode`, or a typo in a variable): fix `.env` and run `docker compose up -d` again.

Quick local check (works in every setup):

```
curl -s http://127.0.0.1:47831/healthz
curl -s http://127.0.0.1:47831/v1/info
```

The first prints `ok rooms=0 splices=0`.

## Step 7, setup A: nginx terminates TLS

nginx listens on the public port, owns the Let's Encrypt certificate and forwards plain bytes to the relay on 127.0.0.1:47832.

**7A.1 Get a certificate.** If nothing on this server uses port 80 yet, stop nginx for a moment and let certbot answer the challenge itself:

```
sudo systemctl stop nginx
sudo certbot certonly --standalone -d relay.example.org --agree-tos -m you@example.org --deploy-hook "systemctl reload nginx"
sudo systemctl start nginx
```

(`you@example.org` is your own address, for expiry notices; it can be any address you read.) If nginx already serves websites on port 80, use its plugin instead and skip the stop and start:
`sudo certbot certonly --nginx -d relay.example.org --agree-tos -m you@example.org --deploy-hook "systemctl reload nginx"`. The files appear in `/etc/letsencrypt/live/relay.example.org/`.
Certbot renews by itself (a systemd timer, check `systemctl list-timers | grep certbot`); the `--deploy-hook` makes nginx pick up each renewed certificate. Renewal needs port 80 reachable:
with `--standalone` and nginx on port 80 it would fail, which is why the plugin is the choice for a server with websites. Rehearse once: `sudo certbot renew --dry-run`.

**7A.2 Install the nginx configuration.** The file `nginx/relay.conf.example` of the deploy folder is the stream configuration. Copy it, put your own name in, and include it from nginx.conf:

```
sudo cp nginx/relay.conf.example /etc/nginx/unciv-relay-stream.conf
sudo sed -i 's/relay\.example\.org/YOUR.DOMAIN.HERE/g' /etc/nginx/unciv-relay-stream.conf
echo 'include /etc/nginx/unciv-relay-stream.conf;' | sudo tee -a /etc/nginx/nginx.conf
```

(Replace `YOUR.DOMAIN.HERE` with your relay's name, for example `relay.mygames.net`.) The `include` line must sit at the top level of nginx.conf, next to `http { }`, not inside it; appending it at
the end of the file does that. If Debian's nginx complains `unknown directive "stream"`, the module is not loaded: `sudo apt install libnginx-mod-stream`. If it complains about `ssl_alpn`,
nginx is older than 1.21.4.

**7A.3 Test and apply.**

```
sudo nginx -t
sudo systemctl reload nginx
```

`nginx -t` must say `syntax is ok` and `test is successful`. Never reload without it.

**Optional, sharing port 443 with a website.** If some players are on networks that only allow 443, nginx can route by the name in the TLS handshake (SNI). This is setup B for the relay
(the relay keeps the certificate; nginx passes the encrypted bytes through) plus nginx: follow Step 7B for the certificate, set in `.env` `RELAY_TUNNEL_PUBLISH=127.0.0.1:47833`,
`UNCIV_RELAY_PROXY_PROTOCOL=true` and keep `UNCIV_RELAY_TRUSTED_PROXY`, then use `nginx/relay-sni.conf.example` instead of `relay.conf.example` (not both). Your website must move to port 8443; read the comments
in that file first, they say exactly what changes in the website's `listen` line. Open 443 instead of 47830 in the firewall; players then type `unciv-relay://relay.example.org:443`.

**Optional, the read-only game list over HTTPS.** `nginx/relay-http.conf.example` explains how to expose `GET /unciv-relay/v1/games` and `/healthz` under your website's HTTPS server for
monitors and curl. Players do not need it.

## Step 7, setup B: the relay holds the certificate

**7B.1 Get a certificate** (needs port 80 free and open; the relay is not using it):

```
sudo certbot certonly --standalone -d relay.example.org --agree-tos -m you@example.org
```

**7B.2 Copy it where the container can read it.** Let's Encrypt keeps its files private to root, and the container runs as the unprivileged user 10001, so the relay gets its own copy
in the `certs` folder of the deploy folder (git ignores everything in it). Put this script in `/etc/letsencrypt/renewal-hooks/deploy/unciv-relay.sh`, so that every renewal repeats it:

```
sudo tee /etc/letsencrypt/renewal-hooks/deploy/unciv-relay.sh >/dev/null <<'EOF'
#!/bin/sh
set -e
NAME=relay.example.org                          # PLACEHOLDER: your relay's DNS name
DEST=/opt/unciv/csharp/Unciv.Relay/deploy/certs  # the certs folder of your clone
cp "/etc/letsencrypt/live/$NAME/fullchain.pem" "$DEST/fullchain.pem"
cp "/etc/letsencrypt/live/$NAME/privkey.pem" "$DEST/privkey.pem"
chown 10001:10001 "$DEST/fullchain.pem" "$DEST/privkey.pem"
chmod 600 "$DEST/privkey.pem"
docker kill --signal HUP unciv-relay-relay-1 2>/dev/null || true   # the relay re-reads the certificate on SIGHUP
EOF
sudo chmod +x /etc/letsencrypt/renewal-hooks/deploy/unciv-relay.sh
sudo RENEWED_LINEAGE=/etc/letsencrypt/live/relay.example.org /etc/letsencrypt/renewal-hooks/deploy/unciv-relay.sh
ls -l certs
```

Edit `NAME` and `DEST` first if yours differ. `ls -l certs` must show both files owned by `10001`. Then do Step 5 (setup B column) and Step 6.
Certificate files are mounted read-only at `/certs` in the container (that is why `UNCIV_RELAY_CERT=/certs/fullchain.pem`).

## Step 7, setup C: no domain, self-signed

Nothing to install: do Step 5 (setup C column) and Step 6. The relay creates its own certificate once (`relay.pfx` in its data volume) and prints its fingerprint:

```
docker compose logs relay | grep RELAY-FINGERPRINT
```

Players pin that value: `unciv-relay://203.0.113.10:47830?fp=<fingerprint>`. Keep the data volume (see Backups): losing it creates a new certificate and a new fingerprint.

## Step 8: check that it works

From the server (all setups):

```
docker compose ps                                     # healthy
curl -s http://127.0.0.1:47831/healthz                # ok rooms=0 splices=0
curl -s http://127.0.0.1:47831/v1/info                # JSON with your contact address
```

From **your own computer** (this tests DNS, firewall, nginx and the certificate together; `203.0.113.10` or the name, as in your setup):

```
openssl s_client -connect relay.example.org:47830 -alpn unciv-relay/1 </dev/null 2>&1 | grep -E "subject|Verif|ALPN"
```

Setups A and B must show your domain in `subject=` and `Verification: OK` (Setup C shows a self-signed certificate and a verification error, which is expected). In setup A
`ALPN protocol: unciv-relay/1` confirms nginx's TLS settings; if the command hangs or says `connection refused`, see Troubleshooting.

**A real join test.** The dedicated server of this repository can register a room on your relay, and the relay then lists it (`Unciv.Server` is built by `dotnet publish Unciv.Server`;
the release folders contain it too):

```
Unciv.Server --port 0 --relay unciv-relay://relay.example.org:47830 --list --list-name "relay test" --print-invite
```

(Setup C: add `--relay-fingerprint <fingerprint>`.) It prints `RELAY-ROOM XXXX-XXXXXX` and an `INVITE-RELAY` line. On the relay server, `curl -s http://127.0.0.1:47831/v1/games` now shows
the game "relay test". A game client with the relay address set (the `url` in `relay.json` of the Unciv user folder, `"unciv-relay://relay.example.org:47830"`) can host and join through it.

## Step 9: tell your players

Give them the address from the table in "Choose your setup", and your contact address. Put the same address in `UNCIV_RELAY_CONTACT` so the relay's `/v1/info` shows it. State what the
relay operator can see: players' IP addresses, room codes, times and byte counts, never game data (design/RELAY.md section 9). Logs older than 7 days are deleted by the relay itself.

## Running it

All `docker compose` commands run in `/opt/unciv/csharp/Unciv.Relay/deploy`.

| Task | Command |
|---|---|
| Status | `docker compose ps` |
| Follow the log | `docker compose logs -f relay` |
| Find a room (abuse report) | `docker compose exec relay sh -c 'grep room=K7QF-3MXP4A /data/logs/*'` |
| Change a setting | edit `.env`, then `docker compose up -d` (recreates the container; running games reconnect) |
| Stop / start | `docker compose stop` / `docker compose start` |
| Remove the container but keep the data | `docker compose down` |
| Remove everything, including the secret and certificate | `docker compose down -v` (do not, unless you mean it) |

**Bans.** One entry per line in `bans.txt` in the data volume: an IP or CIDR network, `key <fingerprint>` or `name <regex>`. A line that begins with `#` is a comment (a `#` after an entry is not).
The relay re-reads the file by itself within about a second; `docker compose kill -s HUP relay` forces it.

```
docker compose exec -T relay sh -c 'echo "203.0.113.0/24" >> /data/bans.txt'
docker compose exec -T relay sh -c 'echo "key ABCDE-FGHIJ-KLMNO-PQRST-UVWXY-Z" >> /data/bans.txt'
docker compose exec relay cat /data/bans.txt
docker compose logs --tail 5 relay            # a malformed line shows up here as policy-warning
```

`allow-keys.txt` (with `UNCIV_RELAY_LISTING=allowlist`) and `deny-names.txt` work the same way.

**Updating.** Fetch the new code, rebuild, restart. The data volume and your `.env` are untouched.

```
cd /opt/unciv && git pull
cd csharp/Unciv.Relay/deploy
docker compose up -d --build
docker compose ps
```

Compare `.env.example` with your `.env` after an update (`diff .env.example .env`): new options appear in the example first, and an unset one simply keeps the relay's default.
The restart tells every host to reconnect (they do, with backoff, and take their room back); players in a running game see a short pause.

**Backups.** Everything that matters is the data volume `unciv-relay_relay-data`: `relay-secret` (keeps room codes stable across restarts: back it up), `relay.pfx` (setup C: the fingerprint
players pinned), and your list files. Your `.env` is the rest. To make a backup file in `~/unciv-relay-backups` (outside the git clone: the file holds the relay's secret and private key, so keep it private and never commit it) and to restore it:

```
mkdir -p ~/unciv-relay-backups
docker run --rm -v unciv-relay_relay-data:/data -v ~/unciv-relay-backups:/backup:z alpine tar czf /backup/relay-data-backup.tgz -C /data .
docker compose stop
docker run --rm -v unciv-relay_relay-data:/data -v ~/unciv-relay-backups:/backup:z alpine sh -c 'rm -rf /data/* && tar xzf /backup/relay-data-backup.tgz -C /data && chown -R 10001:10001 /data'
docker compose start
```

The second and third command are the restore; run them only when restoring. Certificates for setups A and B are re-issued by certbot and are not part of the backup.

**Logs.** `docker compose logs relay` shows the same lines that go to `logs/relay-<date>.log` in the volume. They contain no game data, names, passwords or tokens; connection lines keep the
source IP so abusers can be found. Files older than `UNCIV_RELAY_LOG_RETENTION_DAYS` (7) are deleted by the relay. Docker's own log of the container can grow; to cap it add
`{"log-driver":"local"}` to `/etc/docker/daemon.json` and restart Docker once.

**Starting at boot.** `restart: unless-stopped` and `systemctl enable docker` (Step 1) bring the relay back after a reboot or crash.

## Troubleshooting

| Symptom | Likely cause and fix |
|---|---|
| `docker compose` is unknown | Docker Compose v2 is missing: `sudo apt install docker-compose-plugin`, or reinstall as in Step 1. |
| Container restarts; log says `choose a TLS mode` | `.env` missing or all of `UNCIV_RELAY_TLS`, `_CERT`/`_KEY`, `_SELF_SIGNED` empty. Re-do Step 5. |
| Log says `choose one TLS mode` | More than one of them is set. Setup A: only `TLS=none`. Setup B: `TLS` must be empty. |
| Log says `--public-name is required` | Setups A and C need `UNCIV_RELAY_PUBLIC_NAME`. |
| Log says `Access to the path '/certs/fullchain.pem' is denied` | The files are not owned by uid 10001, or not mode 600/644 (setup B, Step 7B.2). On SELinux systems with a plain `docker run` add `:z` to the mount; compose.yml already has it. |
| Hosts are refused with `host-refused reason=bad-signature` in the log | The name the player typed differs from `UNCIV_RELAY_PUBLIC_NAME` (or the certificate's names). Add the missing name to the comma-separated list. |
| `Bind for 127.0.0.1:47832 failed: port is already allocated` | Another program uses that port: change `RELAY_TUNNEL_PUBLISH` (and `proxy_pass` in nginx to match). |
| nginx: `unknown directive "stream"` | `sudo apt install libnginx-mod-stream` and reload. |
| nginx: `unknown directive "ssl_alpn"` | nginx older than 1.21.4; upgrade nginx. |
| nginx: `cannot load certificate ... No such file` | Step 7A.1 not done yet, or the name in `/etc/nginx/unciv-relay-stream.conf` differs from the certbot name. |
| nginx: `bind() to 0.0.0.0:47830 failed (98: Address already in use)` | The relay container publishes 47830: setup A must use `RELAY_TUNNEL_PUBLISH=127.0.0.1:47832`. |
| Players connect but the log shows `proxy` errors or closed connections right away | Setup A mismatch: nginx has `proxy_protocol on;` but `UNCIV_RELAY_PROXY_PROTOCOL` is empty (or the reverse). The header is accepted only from `UNCIV_RELAY_TRUSTED_PROXY`; look up the source with `docker network inspect unciv-relay_default` and add its subnet. |
| Every player appears with the same IP in the log | The PROXY header is not being used: same cause as the previous row. Per-player limits and bans do not work until it is fixed. |
| Players from the same household are refused (rooms or connections limit) | They share one address. Raise `UNCIV_RELAY_MAX_ROOMS_PER_NETWORK` and `UNCIV_RELAY_MAX_CONNECTIONS_PER_NETWORK`. |
| `openssl s_client` hangs or times out | The firewall (Step 3, both the server and the provider panel) or DNS (Step 2). Test `nc -vz relay.example.org 47830`. |
| certbot: `Timeout during connect` | Port 80 is closed in the firewall or occupied; `sudo ss -ltnp 'sport = :80'` shows who uses it. |
| `docker compose ps` shows `unhealthy` | Open the log. If you set `UNCIV_RELAY_NO_HTTP=true` the check only connects to the tunnel port; otherwise `curl http://127.0.0.1:47831/healthz` inside the container must answer. |
| The disk fills | `UNCIV_RELAY_LOG_RETENTION_DAYS`, `UNCIV_RELAY_NO_LOG_FILES=true`, and the Docker log cap above. |

## Without Docker

`deploy/unciv-relay.service` is a systemd unit for the self-contained build (`dotnet publish Unciv.Relay -c Release -r linux-x64 --self-contained true`). The options go in
`/etc/unciv-relay/relay.json` or in `Environment=UNCIV_RELAY_...` lines; the nginx files of this guide apply unchanged (the relay then listens on `127.0.0.1:47832` with
`UNCIV_RELAY_TUNNEL_PORT=47832`).

## What was tested
