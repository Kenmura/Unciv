## Policy

1. **Key type has a deterministic JVM `hashCode`** (String, Int, Long, Boolean, `HexCoord` need nothing extra; Char, Float and Double are counted here too but have no default, pass `JavaHash.HashCode` explicitly and check C# equality matches `Float.equals` for NaN and -0): port with `JavaHashSet<T>` / `JavaHashMap<K,V>` (`Utils/JavaHashMap.cs`). Iteration order then equals the JVM's (verified against OpenJDK 25 and Kotlin stdlib 2.3.0 in `JavaHashMapTests`). Use the matching constructor: `JavaHashSet<T>()` for `HashSet()`, `HashSetOf` for `hashSetOf(...)`, `ToHashSet` for `.toHashSet()`, `new JavaHashSet<T>(collection)` for `HashSet(collection)`, `new JavaHashMap<K,V>(map)` for `HashMap(map)`.
2. **Key type is an enum or a class without a `hashCode` override** (identity hash): the JVM order differs from run to run, so the Kotlin program is itself nondeterministic when it iterates such a collection. There is nothing to reproduce. Port with an insertion-ordered collection (`List`, `OrderedDictionary`, or the ordered `Counter`), or sort by a stable id when the Kotlin order was only incidental. Record the decision in the ticket notes; membership-only use (`contains`/`add`/`remove`, never iterated) can use any set.
3. **Unknown / inferred** (`hashSetOf()` with the type taken from context, `.toHashSet()`): look at the declaration when porting the file.
4. If the port iterates the collection **only to compute an order-insensitive result** (sum, any, count, set equality), the policy is moot; prefer clarity over emulation.
5. Limits of the emulation: treeified bins (nine or more keys in one bucket of a 64+ table) throw `NotSupportedException`; `HashSet(collection)` sizing follows JDK 19+ (earlier JDKs and Android may order such copies differently, so avoid depending on the order of a copied set).

The audit is a worklist, not a verdict: each row is a place the porting ticket for that file must apply the policy.
