    - Protocol: Hello.modSync (optional), ModFileRequest, ModManifest, ModFileData, Error mod-file-refused, JoinRefused mod-sync-unavailable. A mismatching Hello with modSync=true continues the handshake (host key check, password/invite, key proof) and only the authenticated joiner gets the ModManifest; without the flag the old immediate ruleset-mismatch refusal is unchanged. Invite token is checked, not consumed, on the sync connection (LobbyAdmission.AdmitForModSync, InviteTokens.IsValid) so the re-join works.
    - Core/Net/Mods: ModSyncRules (allow-list = RulesetFile.Values json names only, mod-name rules, caps 2 MiB file / 16 MiB mod / 32 MiB + 8 mods), ModManifestBuilder (build, checksum, client-side Validate), IModFolders. Host (LobbyHost) builds the manifest once per ruleset, serves only listed files once per connection and re-verifies size+SHA-256 when serving.
    - Client.Net/Mods/ModSyncService: plan (missing/different/same), confirm callback (no download without yes), per-file size/SHA/strict-UTF-8 checks, staging folder, staged mod must rebuild to the checksum and load as a Ruleset before the swap, existing different mod kept as .sync-backup-NAME, rollback on failure, HotLoad (RulesetCache.ReloadSingleRuleset on the UI thread + combined hash check). ClientSession: ModSync option, ModSyncResult, ends with mods-synced; JoinScreen shows the confirm panel, hot-loads and re-joins once with the host's hash; App passes the file source and aligns the NewGameForm to the host's rules.
    Deviations / decisions: only ruleset json data is transferred; images, sounds, atlases are NOT (v1), so a mod relying on them shows placeholders. Manifest authenticity = TLS channel pinned to the host key + admission + key proof (no separate manifest signature: the host is the trust anchor and the per-file SHA-256 + checksum bind content). Built-in rulesets are never transferred.
