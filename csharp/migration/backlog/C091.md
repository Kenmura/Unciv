  - Implemented (client-side only, no engine change): GroupMoveModel (Unciv.Assets) + GameScreen wiring. Shift-click an own unit adds/removes it from the selection (MapView.LastClickShift); the group is the selected unit plus extras, drawn enlarged. Clicking a tile twice (preview, go) or right-clicking sends one ordinary MoveUnit per unit: the engine path query is asked right before each command (so earlier moves are in the answer), a refused step is re-pathed once, a target held by a mate falls back to the tiles around it (nearest first), a unit already next to a held target counts as arrived. Order of commands is by distance to the target then id (deterministic). Escort: a two-unit group of one civilian and one military unit at most one tile apart gets an Escort pair / Stop escort menu entry (MenuEntryKind.Group, no command). A pair moves as: both go to one tile that is the first step of either path and that both can reach this turn (military first), the civilian then follows to where the military really stopped; if no common step exists neither moves. A pair remembers its target and the screen continues it at the start of the next turn (two more ordinary moves each) once the viewer's units have movement again. Escort pairs are client memory only (per viewer civ, lost on restart/reload), never in saves or commands.
    Deviations: pairs are not persisted; a pair with an unreachable common step stands still for the turn rather than splitting; the engine's own EscortFormation unit action is untouched (this macro is separate). Group move uses the primary unit's path preview/hint and needs the primary to have movement for the preview step.
    Harness: new scenario group-move (skirmish game) with new ShiftClick step and InputSimulator shift flag; the ticket's gate scenario unit-orders is unchanged and still passes (goldens untouched). Spawned-unit scenarios cannot be replayed headlessly, so group-move uses the skirmish units (warrior, settler, worker).
