- Notes: Phase 5. Created by T268.
  - Implemented slice 2 of host migration: standby replication (details in design/HOST-MIGRATION.md, "Implementation status (T272)"). Deviations and choices:
    - Protocol version 3 (new messages StandbySubscribe/Meta/Snapshot/Entry/Ack); StandbyStatus gained optional GameId (the successor needs the game id to pick its store dir); error code standby-protocol.
    - The stream sends the host's commands.log lines verbatim (StandbyEntry.Line), so the successor dir is an ordinary host game dir and promotion is FileGameStore.Open. The successor log is not rotated (follow-up: standby log rotation/compaction).
    - Resume: haveSeq plus sha256 of the successor's last line; for a store holding only a reset's checkpoint, the checkpoint line stands in. Host continues if its own line at haveSeq hashes the same and the gap <= 2000, otherwise it restarts from a reset snapshot with the log header.
    - Lag: >2000 unacked entries, or no ack for 30 s with entries outstanding. Once lagging nothing is sent until acked >= sent, then a reset snapshot resync. With nothing in flight and the gap already over the limit the host resyncs directly (Lagging is then not observable). Acks sent before the successor saw a reset snapshot are ignored (only ack == ResetSeq counts); a backwards ack or one beyond the log closes the subscription with standby-protocol.
    - Security: designated + accepted authenticated key only (IsAcceptedCandidate on the session key, generic not-designated otherwise, re-checked in every step); revoke/decline/detach/close stop the stream. Client stores a copy only if this process called AcceptStandbyAsync (or the dir already exists) and the game id is a safe dir name; the UI mirror stays the filtered snapshot, only StandbyHaveSeq and a StandbyRejected event are exposed.
    - Pinning in the client now keys on HostSuccessor.Successor != null, not Status == ready (status can now be syncing/lagging while reachable).
    - "ready" before a subscription still only means the probe passed; Syncing/Lagging appear once replication runs. T282 (periodic re-probe) untouched.
    - Test seams: FileGameStore implements IReplicationSource (windowed log reads, Changed callback that only posts a mailbox step); BoundedSendTransport.QueuedFrames drives pacing.
    Follow-ups to consider: standby log rotation on the successor; T275 UI for StandbyHaveSeq/StandbyRejected.
  - Review pass fixes: subscribe throttled (StandbyLimits.MinSubscribeMillis 1 s, Error standby-protocol detail subscribe-rate, stream untouched); acks above SentSeq are a violation, a reset ack needs ResetSeq >= 0; client ignores a status whose game id differs from the joined game, DeclineStandbyAsync closes the store and deletes the copy, restart counter decays after a successful reset. Deferred to T291: stopped-stream state, resubscribe on standby-protocol, successor log rotation/disk cap, off-thread store writes, per-game consent record, reserved names, snapshot cache. Known limit: a client restart request refused by the subscribe throttle waits for the next reconnect.
