- Notes:
  - Found by T249. LobbyHost.AttachConnectionAsync loops on transport.ReceiveAsync while Status != Closed, so after ServerLobby.StartGameAsync attaches the same slot transports to GameHost (whose session reader also reads them) two readers compete for inbound frames. A test that joined a ClientSession through ServerLobby, started the game and submitted a command never got a CommandResult (timed out); the same flow with a GameHost-only host works. Fix: stop the lobby reader for a seat once its session moved to GameHost (or hand the reader over), and add a ClientSession-through-ServerLobby command round trip test. Also decide join-in-progress: LobbySettings.AllowJoinInProgress exists but a new player is refused after start (JoinRefused), only a known key is re-seated. Verify the suspicion by reading the code before fixing.
  -   - Implemented (Claude). Verified suspicion: the lobby reader loop only stopped on Status==Closed, so it kept reading slot sockets after start and stole frames from GameHost.
      - Fix: single reader per socket. LobbyHost.StartGameAsync gives every seated session a hand-over channel; the lobby reader forwards all later frames into it and LobbyHost.GameTransportFor(sessionId) returns an ITransport (sends pass through, receives read the channel, end-of-stream completes it). ServerLobby attaches that transport to GameHost. A handed-over session no longer runs lobby disconnect handling.
      - Join-in-progress decision (deliberate deviation): a KNOWN key authenticating after start is re-seated into the running game (LobbyHost.LateSeated -> ServerLobby attaches to GameHost, which sends the snapshot). A NEW key after start is refused with game-started, even with AllowJoinInProgress=true: seating a new human needs store slot-binding + civ hand-over machinery in GameHost that does not exist. Follow-up if wanted: real join-in-progress (new key takes an AI civ).
      - Late seating is attached through the game actor, so a known player's in-game Ping is answered only once the actor is free; NetFrameLossTests knock for the known key no longer pings while the actor is busy (stranger case still does).
      - Tests: NetLobbyTests (command round trip x5 through ClientSession+ServerLobby, known-key reconnect after start, new key refused game-started).
