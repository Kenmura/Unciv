- Notes:
  - Root cause: test-side races, not the server or the in-memory transport. (1) ClientSession.SetLobbySlotAsync / raw LobbySet sends are fire-and-forget and the host applies them asynchronously, so StartGameAsync(force) right after could start with the slot still on Random (a raw test's next ReceiveMessage<LobbyState> may also be an older broadcast). Seed 42 drew Rome under Gods & Kings by luck but Japan under BNW, so the human was Japan, ReleaseSeat("Rome")/Rome-session counts saw nothing. Fixed with WaitForNationAsync (polls the host's slot until Rome) after every started-game LobbySet. (2) TwoRapidSameKey picked `await await Task.WhenAny(seatedSecond, seatedThird)`: the superseded connection's event stream ends (false) and could win the race, failing a correct server. Fixed with AnyTrueAsync. The server's LobbySet-vs-start ordering is by design (host Start is a host API; clients cannot start). The T359 Gods & Kings pin (TimingSensitiveSettings) is removed; both tests run on the default BNW ruleset (40/40 repeated runs green, 3/20 red before).
  - Review notes (Adversarial Review, changes requested): root-cause part (1) verified (LobbySet is fire-and-forget, HandleLobbySetAsync applies it under the gate asynchronously while StartGameAsync reads slot.Nation under the same gate; WaitForNationAsync is a correct fix and explains the SeatSuperseded "Transport is closed": with Japan seated, ReleaseSeat("Rome") was a no-op, so the start saw an unexplained closed transport). AnyTrueAsync fix (2) is correct. No new suppressions. But the deliverable "both tests pass on BNW with no pin" is not met: in 50 looped runs of the two tests (dotnet test --no-build --filter, dotnet-dev distrobox) 2 failed, one captured: ServerLobby_TwoRapidSameKeyReconnectsAfterStart_* at NetLobbyTests.cs:692 `Assert.All(joins, j => Assert.True(j.Joined))` -> one join returned JoinResult { Joined = False, Code = connection-lost }. Cause (LobbyHost.HandleAuthAsync): the second same-key auth seats itself under the gate, but sends its JoinOk only after leaving the lock; the third auth can take the lock, remove the second as replaced, send its own JoinOk and CloseQuietlyAsync the second's transport before the second's JoinOk goes out, so the superseded connection legitimately sees connection-lost instead of JoinOk. This is a remaining test-side over-assertion (both rapid joins must succeed), not covered by T364's analysis. Fix: assert at least one join Joined, and that the seated/playable one is a Joined one (a superseded one may be refused/lost); re-loop >=50x green. Also re-check whether the same assertion is reachable for other rapid-reconnect tests.
  - Review round 1 follow-up: a third test over-assertion (Assert.All joins Joined) failed ~2/50 because the superseded connection can be closed by the newer one before its JoinOk (connection-lost); now Assert.Contains(joins, Joined). 60/60 looped runs green afterwards.
