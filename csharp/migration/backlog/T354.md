  - Owns RELAY.md R14. A host running two games on one key has one room per game (gameTag); the standby room is a separate unlisted room.
  - Implemented. Wire (additive, protocol version unchanged, a direct-only successor encodes byte-identically): `RelayRoute{relay:"host:port", room}`; `SuccessorInfo.Relay` and `StandbyAccept.Relay` (Endpoints may be empty when a room is given; Port then ignored). A route never carries a relay certificate pin (never taken from a peer). `RelayRoutes` (Core/Net/Relay) normalises every route that arrives from a peer.
    Trust design (deliberate): (1) HOST side: `TlsEndpointProber(Func<RelayEndpoint,RelayDialPlan?>)` dials a relay only if the resolver returns a plan; the default resolver is null (no relay), InProcessHost.Listen(relayEndpoint) installs one that allows only the host's own configured relay, `RelaySettings.Agreed` allows configured + previously agreed relays. An unagreed relay makes the probe fail, so the standby stays `unreachable` and is never announced (no client is ever pointed at it). (2) CLIENT side: a hand-off naming a relay route is followed only when the session has BOTH `ConfirmRelay` and `ConnectRelay`; the route must equal the announced one; `RelaySettings.ConfirmAsync` shows the "Connect through relay X?" prompt once (handshake clock stopped) and remembers a yes in AcceptedRelays, never in Url; a no/throw fails the attempt without dialling. `RelaySettings.ConnectAsync` pins the successor's ANNOUNCED fingerprint inside the splice (ConnectViaRelayAsync expectedFingerprint) before any game byte, plus the existing Welcome.Promotion signature check, so the pinned host key still authenticates the successor whatever relay carries it. The announcement also writes a vouched KnownHosts pin under `relay:port/ROOM`.
    Successor: `StandbyListener(cert, int? port, ..., RelayListener? relay)` keeps an unlisted room (never SetListing) and answers the same probe; `DetachRelay()` + `InProcessHost.Listen(adoptRelay)` hand the registration to the promoted host so the announced room survives promotion (StandbyPromotion does it; relay-only successor binds local port 0).
    Behaviour fix found by the harness: during a hand-off redirect a Welcome{standby:true} from the successor (it is still promoting) is now a retried attempt instead of a terminal `not-host-yet` refusal (the direct path had the same latent race when a standby listener is up).
    Tests: StandbyRelayTests.cs (wire, RelayRoutes, coordinator, probe through a local relay incl. untrusted relay, unknown room, wrong key, standby room limits, DetachRelay, RelaySettings) and HostHandoffTests (R14: graceful hand-off to a relay-only successor through a local SelfSigned relay, prompt-yes remembered once, prompt-no never dials, host refuses to probe an unagreed relay, scripted client rules). UNVERIFIED: no real-GPU/UI; the crash-election promotion (T274) is not in scope here, it reuses the same successor endpoint and ConnectRelay hook.
